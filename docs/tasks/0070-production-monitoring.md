# Task 0070: Production Monitoring Repository Contract

## Status and objective

The repository-side Production Monitoring extension is implemented and locally/synthetically testable. It extends the existing `yolpol-monitoring` project to observe Production without creating a second monitoring stack or bridging Staging and Production networks. This task does not mutate the VPS, create a database login or real credential, contact Telegram, change DNS/Cloudflare, activate public traffic, or claim that Production Monitoring is live.

Task 0059 remains the historical record for the original Staging monitoring foundation. Before this task, PostgreSQL, Operations, and internal web collection were Staging-only; the shared host collectors and alert pipeline already existed.

## Shared architecture and Production topology

Exactly one Compose project remains authoritative:

| Scope | Services |
| --- | --- |
| Shared | `prometheus`, `alertmanager`, `node-exporter`, `cadvisor` |
| Staging-only | `postgres-exporter`, `operations-exporter`, `blackbox-exporter` |
| Production-only | `postgres-exporter-production`, `operations-exporter-production`, `blackbox-exporter-production` |

Prometheus, Alertmanager, host metrics, Docker visibility, retention, loopback UI bindings, bounded logs, and named monitoring volumes are not duplicated. Grafana remains deferred. No exporter publishes a host port, and cAdvisor remains the only service with Docker socket access.

The added collectors contribute 384 MB and 0.40 CPU of configured ceilings. The complete ten-service stack totals 1,792 MB and 1.90 CPU. These values are Docker maximums, not reservations; shared-service limits were not increased.

## Network and credential isolation

The Staging PostgreSQL and Operations exporters join only `monitoring` plus `yolpol-staging_backend`. Their Production counterparts join only `monitoring` plus `yolpol-production_backend`. Staging Blackbox joins only `monitoring` plus `yolpol-staging-ingress`; Production Blackbox joins only `monitoring` plus `yolpol-production-ingress`. Blackbox collectors join no backend, database/Operations collectors join no ingress, no collector joins both environments, and only Alertmanager joins monitoring egress.

Production uses four fixed file-backed secret paths under the root-only `0700` Monitoring secrets directory:

- `production-postgres-exporter-uri`, `production-postgres-exporter-user`, and `production-postgres-exporter-password`: `65534:65534`, mode `0400`;
- `production-operations-database-url`: `10001:10001`, mode `0400`.

These paths are distinct from every Staging path. Values do not enter `runtime.env`, Compose YAML, process arguments, logs, or Git. Bootstrap installation requires all values in the closed Monitoring JSON schema and validates the complete input before atomically installing any file. No real value is generated by this task.

## PostgreSQL and Operations metrics

The Production PostgreSQL Exporter uses the same deliberately limited built-in collector set as Staging. Statement/query text collection, arbitrary database auto-discovery, and custom SQL are not enabled. Its target is labelled `environment="production"` by Prometheus.

The Production Operations Exporter reuses the repository-owned Operations Metrics image with fixed `YOLPOL_DEPLOYMENT_ENVIRONMENT=production` and its own database URL file. The exporter continues to issue only one aggregate query across `inquiry_outbox`, `conversation_translation_jobs`, and `conversation_ai_response_jobs`. It does not select or label Customer, inquiry, conversation/message content, recipient data, product pricing, prompt, or provider payload data. Metrics retain only fixed `environment` and `queue` labels.

Monitoring image authority deliberately remains the authenticated Staging release manifest. The same single immutable `YOLPOL_OPERATIONS_METRICS_IMAGE` is configured for both environment-specific instances, but automated Staging deployment and rollback may update only the Staging instance. Before root activates or recreates the Production collector, root must review compatibility with both active releases and immutable digests; a newer Staging-authorized image must not be applied blindly when Production remains on an older release. This preserves the established host-infrastructure authority without modifying Production release authority. Per-environment monitoring image authority requires a separate reviewed change.

The intended Production database role is a dedicated login with `CONNECT` on the confirmed Production database, membership in `pg_monitor`, `USAGE` on `public`, and `SELECT` only on the three approved queue tables. One Production monitoring login can safely supply both the PostgreSQL Exporter's split files and the Operations Exporter's full URL because their combined least-privilege role is exactly that contract. The file formats remain separate. Actual SQL execution, password creation, grants, and rotation are later reviewed root/VPS operations; no Drizzle migration is added.

## Internal web and container monitoring

Production Blackbox resolves only the stable `production-web` alias through `yolpol-production-ingress` and probes:

```text
http://production-web:3000/api/health/live
http://production-web:3000/api/health/ready
```

It does not probe `https://yolpol.com`, follow a temporary public redirect, or imply DNS/TLS cutover health. Prometheus preserves `environment="production"` on both probe targets.

cAdvisor remains shared. Exact `com.docker.compose.project="yolpol-production"` rules cover the continuously required `web`, `postgres`, `inquiry-notifications`, `conversation-translation`, and `conversation-ai-fallback` services. Equivalent Staging rules retain `yolpol-staging`. Migration, backup, Staff, Telegram, and IndexNow profile/one-shot services are intentionally excluded. Shared ingress retains one `environment="shared"` presence alert.

## Alerts and inhibition

Environment-labelled rules now provide equivalent Production coverage for internal liveness/readiness, PostgreSQL exporter availability and connection pressure, Operations Exporter availability, queue age/count, required container absence, and scrape failure. Host resource alerts remain `environment="host"`; Prometheus/Alertmanager targets remain `environment="monitoring"`.

All Alertmanager inhibition relationships include `environment` in their equality keys. Warning-versus-critical, liveness-versus-readiness, and PostgreSQL derivative inhibition therefore cannot cross from Staging to Production or from Production to Staging even when both environments emit the same alert name.

## Production backup state

`operations-exporter-production` mounts `/opt/yolpol/production/backups` read-only and defaults `YOLPOL_MONITORING_PRODUCTION_BACKUP_ENABLED=false`. Disabled state is exported with `environment="production"`, while missing, scan-failure, and stale alerts remain gated on the enabled metric and do not fire. The exporter mounts no age identity, does not decrypt artifacts, and enables no schedule, creation, pruning, retention, restore, or PITR behavior. Local encrypted-pair inspection is not a claim that Phase C2 off-server durability is monitored.

## Bootstrap, wrapper, and fail-closed policy

The bootstrap and restricted wrapper require the four new fixed files with their exact owners and modes. Monitoring runtime validation requires exact Production network names, paths, disabled backup state, and existing resource limits. Resolved Compose policy fixes the complete service set, image, command, environment, network, mount, secret, port, security, and resource contracts. Adversarial tests reject cross-environment backend/ingress attachment, Staging secret reuse, the wrong Production backup mount, exporter port publication, exporter egress, and Docker socket injection.

No generic Monitoring command, arbitrary Compose surface, operator Docker permission, or wider sudo rule is added. The existing `deploy-operations-exporter` internal primitive and the `pull-staging` path name only the Staging Operations Exporter. Neither Staging deployment nor Staging rollback may pull, recreate, or otherwise mutate the Production collector. Production activation and any later recreation remain explicit root-controlled operations subject to the compatibility review above.

## Validation strategy

Static tests prove the singleton shared services, environment-specific network and secret topology, no exporter ports, cAdvisor-only socket access, fixed targets/labels, Production alert expressions, disabled backup behavior, and environment-scoped inhibition. Official `promtool`, `amtool`, and Blackbox configuration checks validate the monitoring files.

The disposable harness creates separate synthetic Staging and Production PostgreSQL databases, backend networks, ingress networks, and web aliases. It uses synthetic credentials and `alertmanager.local.yml`, expects twelve healthy Prometheus targets and four successful web probes, verifies both Operations Exporters' fixed labels/privacy, inspects actual collector network membership, and exercises graceful shutdown. Cleanup removes only exact harness-owned containers and networks; it never uses `down -v`, volume/system pruning, or a real database/provider.

Final repository validation passed:

- `pnpm test:monitoring`: 2 files and 14 tests;
- `pnpm test:monitoring:disposable`: 12 healthy targets, four successful environment-specific probes, no Telegram attempt, and no named-volume deletion;
- `pnpm test:deployment`: 6 files and 61 tests;
- `pnpm test:bootstrap`: 1 file and 8 tests;
- `pnpm test:release`: 3 files and 32 tests;
- `pnpm test:deployment:disposable`: 26 Linux bootstrap/wrapper tests;
- full `pnpm test`: 241 files and 2,402 tests;
- `pnpm lint`, `pnpm typecheck`, and `pnpm db:check`;
- `pnpm build`: 117 generated static pages plus dynamic routes;
- Prometheus configuration and 37 rules plus their rule tests, both Alertmanager configurations, and Blackbox configuration through the official pinned tools;
- `git diff --check`.

The managed Windows sandbox returned `uv_os_get_passwd ... ENOMEM` for a child `tsx` process and Drizzle, so those unchanged checks were repeated outside that sandbox and passed. This was an execution-environment boundary, not a product-code workaround.

## Activation boundary and deferred work

The precise post-task statement is: **the Production Monitoring repository contract is implemented and validated; live Production collector credentials, database-role provisioning, contract installation, and VPS activation remain operational steps.**

Also deferred are live Telegram delivery testing, periodic Production backup scheduling, a real Phase C2 off-server provider and durability monitoring, the public `https://yolpol.com` DNS/TLS probe after cutover, and an independent off-host watchdog. Prometheus on the same VPS cannot detect total VPS or Prometheus-host loss. Public Production activation and DNS/Cloudflare changes remain separately approved operations.
